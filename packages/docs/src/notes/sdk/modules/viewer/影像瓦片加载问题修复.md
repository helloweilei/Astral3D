# 影像瓦片加载问题修复

本文档整理 Astral3D 地形影像（`ImageryLayer`）在实现与优化过程中遇到的**核心加载/渲染问题**、根因与最终修复方案，便于后续维护与排查。

## 架构概览

```
IAppProject.terrain
        │
        ▼
   Terrain (Viewer 模块)
        │
        ├── ImageryLayer ── GeoUtils / ImageryProviders
        └── Tiles3DLayer
```

影像瓦片流程简述：

1. 根据配置计算当前 Level 与加载范围（bounds）
2. 按瓦片索引分批创建 Mesh + 纹理
3. 延迟卸载超出范围的瓦片
4. 每帧由 `Terrain.update()` 驱动，必要时扩展相机 `far` 并重绘

---

## 问题一：旋转/缩放时频繁闪烁（Level 未变）

### 现象

- 锁定 Level 或 Level 尚未变化时，旋转相机或缩放仍出现边缘闪烁
- 表现为瓦片边界锯齿状变化，或感觉「两张图在切换」

### 根因

1. **视锥求交不稳定**：早期用 `getGroundBoundsFromCamera`（NDC 四角与地面求交）计算加载范围，相机旋转时瓦片索引每帧变化，触发大量增删
2. **裁剪中心错误**：瓦片数量超上限时 `clampBoundsTileCount` 以 bounds 几何中心裁剪，而非相机目标点，视域被裁到画面外
3. **定时重规划**：固定间隔强制重算瓦片计划，造成无意义的卸载/重建

### 修复

| 措施 | 实现 |
| --- | --- |
| 稳定视域 | 新增 `getStableViewBounds`：以目标点 + 视距 + FOV 估算半径，**旋转相机不改变范围** |
| 固定范围裁剪 | `fixedBounds` 或 `lockLevel` 时，裁剪中心改为 **bounds 地理中心** |
| 按需重规划 | 仅当 `tileRangeKey` 变化时才 `planVisibleTiles` |
| 卸载缓冲 | `TILE_REMOVAL_DELAY_MS = 8000`，`REMOVAL_HALO_TILES = 3`，缩小视域时旧瓦片保留更久 |
| Level 迟滞 | `resolveImageryZoom` 加宽上下切换阈值，避免临界距离来回跳 Level |

## 问题二：两个 Level 的 PNG 频繁切换

### 现象

- 缩放或移动时，同一区域像在两个分辨率的底图之间快速切换
- 即使开启「固定范围 + 锁定 Level」仍可能出现

### 根因

1. **多 Level 共存**：zoom 切换过渡期曾保留旧 Level 瓦片 15s，与当前 Level 瓦片**共面叠加**
2. **Z-Fighting**：所有瓦片位于 `y = 0`，`depthWrite: true` 时 GPU 深度缓冲在两层纹理间交替
3. **配置切换残留**：从动态 Level 切换到锁定 Level 时，未清除其他 Level 的瓦片缓存

### 修复

| 措施 | 实现 |
| --- | --- |
| 单 Level 策略 | `purgeTilesAtOtherZoom`：Level 变化时**立即清除**其他 Level 瓦片 |
| 渲染隔离 | `depthWrite: false`、`depthTest: false`，`frustumCulled: false` |
| 纹理就绪再显示 | 加载完成前 `mesh.visible = false`，避免灰色占位闪烁 |
| 配置变更重建 | `lockLevel` / `fixedBounds` / `tilePadding` 等变更时 `clearTiles()` |

## 问题三：缩放较大或较小时地图消失

### 现象

- 拉远或拉近相机时，整片影像消失或仅剩局部
- **手动增大相机 far 后恢复，闪烁同时消失**

### 根因

**相机默认 `far = 100km`**，而低 Level 单块瓦片可达 **~391km**（Level 10）。瓦片顶点超出远平面被投影裁切，相机微动时裁切边界变化，表现为闪烁或「地图消失」。

### 修复

`Terrain.ensureCameraFarForImagery()` + `ImageryLayer.getRequiredCameraFar()`：

- 根据当前加载 bounds 四角与瓦片尺寸，计算相机到最远点的距离
- 若 `requiredFar > camera.far`，自动扩展 `far` 并 `updateProjectionMatrix()`
- **只增大、不缩小**用户手动设置的 far

典型值：Level 10 下 far 会自动扩至 **400km+**。

## 问题四：视锥剔除导致大块瓦片时隐时现

### 根因

Level 较低时单瓦片尺寸极大，Three.js 默认 **视锥剔除** 使用的包围球与实际可见区域不匹配，相机角度变化时整块被错误剔除。

### 修复

- `ImageryLayer.group.frustumCulled = false`
- 每个瓦片 `mesh.frustumCulled = false`

---

## 问题五：动态模式下边缘瓦片 churn

### 根因

动态加载时视域随视距变化，边界瓦片反复进入/离开 active 集合；新建瓦片灰色占位 + 旧瓦片卸载造成边缘抖动。

### 修复

- 扩展圈 `tilePadding` 可配置（默认 3）
- 卸载延迟 + halo 缓冲（见问题一）
- 分帧创建：`MAX_CREATE_PER_FRAME = 24`，`MAX_ACTIVE_TILES = 320`

---

## 问题六：影像源 URL 与 provider 不匹配

### 现象

切换到「自定义 URL」后，输入框仍显示 OSM 默认地址。

### 修复

`resolveImageryUrlForProvider(provider, currentUrl)`：

- 切到 `custom`：URL 为空或为 OSM 默认值 → 填入高德默认 URL
- 切到 `osm`：URL 为空或为自定义默认值 → 恢复 OSM URL
- 用户手动修改过的 URL **不会被覆盖**

默认地址常量：

```ts
DEFAULT_OSM_TILE_URL    // CyclOSM OpenStreetMap
DEFAULT_CUSTOM_TILE_URL // http://webst02.is.autonavi.com/appmaptile?style=6&x={x}&y={y}&z={z}
```

## 关键常量

`ImageryLayer.ts`：

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `MAX_ACTIVE_TILES` | 320 | 同时活跃瓦片上限 |
| `MAX_CREATE_PER_FRAME` | 24 | 每帧最多新建瓦片数 |
| `TILE_REMOVAL_DELAY_MS` | 8000 | 卸载延迟（毫秒） |
| `REMOVAL_HALO_TILES` | 3 | 卸载判定额外缓冲圈 |
| `MAX_TILE_CACHE` | 512 | 内存缓存上限 |

默认相机（`App.ts` / 编辑器）：

| 参数 | 默认值 |
| --- | --- |
| `near` | 0.01 |
| `far` | 100000（100 km，地形启用后会自动扩展） |

## 推荐配置

### 数字孪生（固定区域、最稳定）

```
fixedBounds: true
lockLevel: true
lockedLevel: 14   // 按精度需求调整
tilePadding: 3
bounds: { west, south, east, north }  // 业务范围
```

### 自由漫游

```
fixedBounds: false
lockLevel: false
minZoom / maxZoom: 按场景尺度设置
```

低 Level（8–10）覆盖大范围时，务必依赖 **自动 far 扩展**，不要手动把 far 限制在 100km。

## 排查清单

| 症状 | 优先检查 |
| --- | --- |
| 旋转就闪 | 是否开启动态视域；尝试 `fixedBounds` |
| 两个 Level 交替 | 是否刚切换 Level；确认 SDK 已含单 Level 清除逻辑 |
| 整图消失 | 相机 `far` 是否过小；Level 10 需 >400km |
| 边缘锯齿 | 正常 tile 矩形边界；增大 `tilePadding` 或缩小 bounds |
| 自定义 URL 不对 | provider 是否为 `custom`；检查 `resolveImageryUrlForProvider` |
| 天地图跨域 | 开发环境需 Vite 代理或 HTTPS 源 |
